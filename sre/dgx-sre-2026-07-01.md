## The question

A proposal was brought for review (explicitly no changes before feedback):
enable vLLM's automatic prefix caching (APC) on the MTP build, because the
agent-loop workload re-sends the whole conversation as a shared prefix each
turn — APC would make prefill pay only for new tokens. Nothing needed
changing on the drive-tagger side; it's purely a server flag.

**Origin** — this didn't come from abstract reasoning. It came out of a
`DT_PROVIDER=dgx` drive-tagger run earlier the same day (client-side session
`88069623`, "add-llm-endpoints", 2026-07-01): the user watched decode tok/s
start high and *decay across the agent loop* and asked "are we doing more and
more prefill per loop?", then "is there anything we can do to make the
pre-fill go faster using kv caching?" That question generated the proposal
reviewed here. The symptom is exactly the shared-growing-prefix cost APC
targets.

## The review

Right instinct, wrong in two ways:

1. The proposed command used an `EXTRA_FLAGS` knob that **didn't exist** in
   the MTP script — it would have silently no-op'd and come up clean
   *without* APC, a false "it works." The real knob (`PREFIX_CACHING=1`)
   existed only in the plain script.
2. The suspected blocker (MTP compatibility) was secondary. The real open
   question was the **hybrid architecture**: Qwen3-Next's Gated DeltaNet
   layers carry recurrent state, not radix-cacheable KV blocks, so APC might
   refuse or silently do nothing. Also flagged: `ssh spark` is production,
   and spark2 wasn't free either — it was mid-DFlash-experiment with a live
   client (192.168.1.241) polling it.

The plan that replaced it: test APC alone on the plain build first, then
port the knob to the MTP script, with a real measurement plan (fixed-prefix
TTFT probe + watch the prefix-cache hit counter — APC is invisible to the
usual coherence/tok-s smoke test).

## Execution (user approved tearing down DFlash on spark2)

- Swapped spark2 from the DFlash Coder-30B experiment to plain 80B + APC.
  **APC engages on the hybrid** — vLLM 0.22.0 auto-switches the Mamba cache
  to experimental 'align' mode.
- **Measured with `~/apc_probe.py`** (~7k-token fixed prefix): cold TTFT
  5.94s / 0 hits → warm **0.57s / 6432 hits (~92% prefix hit, ~10× TTFT)**,
  repeat-controlled. The align block size (1072 tokens) explains the ~8%
  miss.
- Ported `PREFIX_CACHE_ARGS` into the MTP script and relaunched spark2 with
  **APC + MTP together**: warm ~5520 hits (~79%), TTFT ~6.7s → ~1.0s.
- **Clean same-prompt A/B for MTP degradation** (temp 0, 300-token code-gen,
  spark1 as MTP-only control): 76.1% accept / 2.52 tok-per-step with APC vs
  77.1% / 2.54 without — within noise. **APC and MTP compose: prefill win +
  decode win, no trade.** That result justified the production rollout.
- **Rolled onto spark1 production**: ~10 min restart, warm probe 5520 hits /
  TTFT 0.578s, coherent; all clients reconnected on the unchanged served id.

## Follow-ons (same session, after rollout)

- **Config parity verified byte-for-byte.** `docker inspect vllm-chat
  --format '{{json .Args}}'` on both boxes diffed **identical** — same model,
  same image (`vllm/vllm-openai:v0.22.0-aarch64`), and every vLLM flag
  (`--enable-prefix-caching`, MTP-2, seqs 3, util 0.80, 256K, fp8 KV, hermes).
  The only real difference between the boxes is that spark2 also runs the
  Ollama embed sidecar (port 11434) — which is why its KV pool is a touch
  smaller (3.54× vs spark1's 3.82× @ 256K), not a config drift.
- **New skill `spark-status-conform`.** Reconciles live box state against
  `current-setup.md`: reads the doc, inspects both boxes, prints the drift,
  then — on the user's call — either conforms the **boxes** to the doc (runs
  the documented spin-up) or conforms the **doc** to reality. Safety: it never
  synthesizes a spin-up command (lifts it verbatim from the doc's banner) and
  never changes a box without an explicit yes for that box.
